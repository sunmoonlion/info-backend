日期：2026-09-12。Luna 单人实施、自测；源码候选，**未升级业务库、未部署**。
基线 `info-backend@33f4a1f9444b89f41eaf00a2c4256d76e78b4881`；总处置清单在 k8s

## 身份语义与兼容边界

`app/domain/info_identity_v1.py` 固定 `info.canonical.v1`。HTTP(S) 主机按当前锁定 HTTPX
的 ASCII/IDNA 表示、IP 按规范写法；scheme/主机大小写、默认端口、空路径与 fragment
归一。路径大小写、尾斜线、百分号编码、查询参数及顺序、空查询标记、主机尾点保留。
不去追踪参数、不排序查询、不把 HTTP/HTTPS 或不同端口合并，不采信网页 canonical 标签。
升级解析依赖须重跑策略向量；改变等价关系必须另立 v2 和迁移，不编辑已用于 0008 的 v1。

`canonical_url` 保留最初写入值，不覆盖历史；新 `canonical_identity` 是版本前缀加规范化 URL
的 SHA-256 派生索引，不是第二份文档主档。身份全 Info 域有效，继续沿用跨来源 URL 归并语义。
遇到同键但规范化 URL 不同（损坏或摘要碰撞）失败关闭，不附着到错误文档。
URL 为 NULL 的旧占位文档保持无键，不凭空为它推断来源。

`upload://filename` 按原字符串保留，包括大小写、空格、#。**这仍是现有 Admin 上传的同名
版本语义，不是未来用户/工作区/本地文件的身份方案。**客户文件隔离必须随新产品身份/授权
统一设计，本包不把同名文件推广为跨客户同一文档，也不自动拆分已经存在的上传历史。

数据库对非空 URL 强制要求 64 位小写十六进制键并唯一；URL 和身份键创建后不可更改。
正常状态、当前版本、治理 metadata 仍可更新。摘要推导由冻结的应用/迁移函数承担，DB
约束不是能辨认任意恶意 SQL 伪造摘要的授权机制；业务 principal 仍须限制为受信写入方。

## 写入与版本并发

`_find_or_create_document` 使用 `INSERT … ON CONFLICT DO NOTHING` 仲裁首次创建，
随后按身份键 `FOR UPDATE` 读取，并刷新已加载的 ORM 实例，避免读取旧 current_version。
不在冲突时覆盖现有标题/来源/版本指针。

`_next_version_no` 再确认持有文档行锁，才读取 MAX+1。锁覆盖版本写入、current_version
更新以及索引 Outbox 的同一事务；原 `(document_id, version_no)` 唯一约束继续保留。
失败回滚不消耗版本、不留索引意图；上传、正常抓取、抽取失败记录均使用同一入口。
未变内容的重复抓取保持复用当前版本，不把上传原本的“每次一个版本”偷偷改成去重上传。

新 `info_document_version.write_protocol_version=1` 为存储写协议标记，有 **Python 默认值、
无数据库默认值**。迁移把既有行纳入该存储协议；这不声称历史版本由新算法创建。
它使旧二进制向既有文档插入版本时也失败，不能只拦住首次创建文档而漏掉老版本写路径。
新程序在旧库缺列/缺约束时同样拒绝写入，不做兼容性静默回退。

## 迁移清单与运行前置

| 项 | 本包 |
| --- | --- |
| 单链 revision | `20260911_0007 → 20260912_0008` |
| `info_document` | 新派生列、唯一/格式约束、URL/身份不可变 trigger/function |
| `info_document_version` | 新必填写协议列及值检查；原版本唯一键不变 |
| 不改 | 原 URL、ID、时间戳、内容、版本/制品/Outbox/下游引用；原 URL 普通索引保留 |
| 所有者/消费者 | Info 单逻辑库；同一后端的 API/Worker 写入；下游契约不变 |
| 数据量 | 本包只核查测试库；实际库行数/冲突未知，必须运行只读核查 |
| 角色/Secret | 现有 Info DB/Migration 角色引用，不写凭据；本包不是数据库角色/凭据迁移 |
| 备份 | 一次性库真实 pg_dump/pg_restore 演练；实际库备份及恢复验收仍待切换前完成 |
| 旧写边界 | 缺身份键的新文档、缺写协议的新版本、修改旧身份均被 DB 拒绝；不是撤销凭据 |

迁移只支持在线连接的受控 Migration Job，不支持无数据核查的 `--sql`；API/Worker/Scheduler
不运行迁移。**先停写/排空执行器再升级，再启动匹配源码。**不以约束错误替代运维停写。
迁移锁住文档写集合，使用 500 行主键分页核查，随后分批回填；旧 URL/ID 不重写。
上限 100,000 行，超限明确报 incomplete/失败，须另做大表方案，不截断后报告成功。
重复、非法 URL、摘要冲突都会拒绝升级；整个 revision 事务回滚，不自行选胜者或删数据。
不能把本批的测试库 `ready=true` 当成业务库已经可以升级。

受权环境中的只读核查（目标库连接经现有配置注入，最好使用只读角色）：

```bash
cd app
uv run python -m app.cli.identity_preflight
```

明确使用 REPEATABLE READ / READ ONLY 事务，仅查询文档 ID/原 URL；输出数量、样本 ID
和 ready/complete，不打印 URL 参数。冲突/超限退出码 2。ready 只表示 v1 回填前提满足，
不是授权、备份完成、已迁移或全库完整性审计结论。

回滚：先停新写入，Migration Job 降到 0007，再回退程序；仅撤销本包派生列、协议列、
约束及 trigger/function，保留全部文档/版本/投递数据。回滚会重新开放旧并发风险，不应
不经评估就恢复高并发写入；重新前滚必须再核新产生的冲突。不能在业务库里试错式来回升级。

- 新专项覆盖保守归一/差异保留、8 并发创建与版本分配、6 同名上传、未变内容复用、
  stale ORM 刷新、事务回滚、摘要冲突拒绝、旧写拒绝、迁移冲突和 503 行跨批次扫描。
- 实际 Alembic 从空测试库升到唯一 `20260912_0008 (head)`；不是只有静态迁移链检查。
- PostgreSQL 17.6 一次性库种入文档、版本、索引 Outbox 各 1 行；真实逻辑备份流恢复到
  独立测试库；恢复库实际降到 0007、再升到 0008 后，三个主表及 alembic_version
  与原库逐行 JSON 仍完全相同。
- 故障注入让前置核查错误放行重复数据，实际唯一约束仍拒绝升级；回填及 DDL 全部回滚，
  原有两行文档保持不变，不留下半迁移列。
- 原迁移异常（流式游标阻止同事务 DDL）由真实数据库暴露，已改为无存活游标的主键分页。
- 对象存储/HTTP 仍用注入；对象孤儿问题由 B4 处理，不因 DB 事务回滚就声称 S3 写也回滚。
- 本包未做业务库扫描、业务库备份恢复、正式角色权限矩阵、KIND 部署及运行切换验收。
